# 写真の追加と管理

2026-10-10 時点のコードとコミット済み `export/` を確認した手順。

## 管理画面から追加する

1. [管理画面の画像ライブラリ](https://admin.tomokichidiary.com/#/media) を開き、「アップロード」で写真を選ぶ。複数選択できる。
2. 本文に入れる写真は、ライブラリの「URL」で写真の URL をコピーする。
3. [記事一覧](https://admin.tomokichidiary.com/#/articles) から対象の記事を開く。
4. 記事の「画像」パネルで「ライブラリから選ぶ」を押して写真を登録する。ここから直接アップロードすることもできる。
5. 用途（カバー・本文など）、代替テキスト（必須）、必要ならキャプションを設定し、「画像を保存」を押す。最初に追加した写真は、既存のカバーがなければカバーになる。
6. 本文中にも表示したい場合は、「本文（Markdown）」の表示したい位置へ次の形で差し込む。URL は手順 2 でコピーしたものを使う。

   ```markdown
   ![写真に写っている景色の説明](コピーした写真のURL)
   ```

7. 「下書きを保存」し、公開チェックを確認して「変更を公開」（新規記事は「公開する」）を押す。

「画像」への登録は写真と記事の関連付け。カバーは記事の先頭や一覧に使われるが、本文用の関連付けだけでは本文に自動挿入されない。本文での位置は Markdown で指定する。登録したキャプションも本文には自動表示されないので、本文で見せる説明は写真の下に文章として書く。

アップロードできる形式は JPEG・PNG・WebP・AVIF・GIF。API の上限は 1 ファイル 20MiB。同じ内容のファイルは SHA-256 で判定し、既存の写真を再利用する。

## どこに保存されるか

| 対象                             | 保存先                                                              | 内容                                                                                                   |
| -------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 既存写真の原本                   | `media/images/<国・地域>/<ファイル名>`                              | このリポジトリの原本。現在の `export/media.json` の 386 件はすべてこの形式で、ローカルにも全原本がある |
| 管理画面からアップロードした原本 | Cloudflare R2 の `originals/<ハッシュ先頭2文字>/<SHA-256>.<拡張子>` | API が直接保存する。ローカルの `media/` には自動保存されない                                           |
| 配信用の画像 URL                 | `https://media.tomokichidiary.com/<保存キー>`                       | R2 の独自ドメイン。サイトの Worker に写真原本は含まれない                                              |
| 写真の管理情報                   | D1 の `media_assets`                                                | ID、保存キー、形式、幅・高さ、容量、SHA-256、作成日時                                                  |
| 記事との関連付け                 | D1 の `article_media`                                               | 記事 ID、写真 ID、用途、順序、代替テキスト、キャプション                                               |
| ビルド用の管理情報               | `export/media.json`、`export/relations/article-media.json`          | データベースから書き出したスナップショット。手編集しない                                               |
| 本文の写真位置                   | 記事 revision の Markdown → `export/articles/<slug>.md`             | `![説明](URL)` の位置が表示位置になる                                                                  |
| 軽量な派生画像                   | `.cache/images/` → R2 の `_img/`                                    | AVIF・WebP、幅 340・704・1408px を基準に原本以下のサイズで生成する。再生成できるので Git に保存しない  |

代替テキストとキャプションは写真そのものではなく、記事との関連付けに保存される。同じ写真を別の記事で使うときは、その記事に合わせた説明を付けられる。本文の Markdown の代替テキストは、その Markdown に書いた説明が使われる。

## 公開サイトへの反映で残っている手作業

公開サイトは D1 を直接読まず、コミット済みの `export/` から静的生成する。管理画面の「公開」は D1 の公開状態を変える操作で、書き出し・Git 更新・サイトの再ビルドを起動する処理は現在ない。

さらに、現行の `pnpm export:data` が読むのは **ローカルの `.data/tomokichi.db`**。本番管理画面で変更した D1 を取得するコマンドではない。本番で追加した記事・写真の情報をローカルへ同期してから書き出す必要があり、その同期を自動で行う手順は現行の scripts にない。`pnpm db:restore-local` は既存 `export/` の復元なので、本番の最新変更を取り込む操作にはならない。

派生画像もローカルの `media/<保存キー>` を原本として生成する。そのため、管理画面でアップロードした写真を派生画像の対象にする場合は、R2 の原本を同じキーのパス（例: `media/originals/ab/<ハッシュ>.jpg`）へ取得する必要がある。現行の本文画像の最適化は `/images/` で始まる URL が対象で、ライブラリでコピーした絶対 URL の写真は原本のまま表示される。

**管理画面で写真を登録して本文に入れるところまではできるが、公開サイトへの反映までを管理画面だけで完結させるには同期・ビルドの接続が必要。** 写真原本を `media/` へ置くだけでも、管理情報や本文は自動登録されない。

ローカルのデータベースと原本が最新になった後の処理は次の順。

```bash
pnpm export:data
pnpm media:build
pnpm media:sync
```

その後、`export/` と追加した `media/` の原本を Git に含め、[リリース手順](OPERATIONS.md#releasing) に従ってビルド・デプロイする。`main` への push は CI 通過後にデプロイを起動する。ローカルで編集した内容を本番 D1 へ反映する場合の seed 手順もリリース手順に従う。

## 記事本文での表示サイズ

写真は縦横比を維持し、本文の幅を超えない。高さの上限は **640px または画面の高さの 80% の小さい方**。縦長写真は中央に収まり、小さい原本は無理に拡大しない。調整箇所は `apps/web/src/styles/prose.css` と `apps/web/src/lib/images.ts`。

カバーや関連リンクのサムネイルはそれぞれの枠に合わせた表示で、本文写真とは別のサイズ設定。
