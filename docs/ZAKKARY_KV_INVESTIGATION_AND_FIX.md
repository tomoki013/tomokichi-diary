# Zakkary WebのKV書き込み過多 調査・原因特定・修正指示書

対象は本番Worker `zakkary-web` と、その公開データキャッシュ `VINEXT_KV_CACHE`。目的は、ZakkaryのWeb・ログイン・店舗更新を維持しながら、同じCloudflareアカウントのKV書き込み枠を使い切る状態を解消し、Tomokichi DiaryのOAuth登録・トークン発行・更新を安定させること。

本書作成時点の許可範囲はZakkaryの読み取り専用調査。調査結果と修正候補をレビューできる形にしてから、プレビューへの反映と本番変更に進む。

## 1. 確認済みの事実と未特定事項

| 項目                        | 確認済みの事実                                                                                                                                                                                                                    |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Diaryで起きたこと           | 2026年11月8日、Analytics・Operator両方のOAuthトークン経路がHTTP 500を返した。Workerの例外は `KV put() limit exceeded for the day`。Analyticsのレポート処理まで届いていない。                                                      |
| 書き込みの内訳              | 同日のCloudflareメトリクスで確認した直近12時間に、`zakkary-web-vinext-kv-cache` は約1,100件、`tomokichi-diary-analytics-oauth` は20件。ダッシュボードの表示値は書き込み操作数であり、すべての操作が成功したことを示す値ではない。 |
| Zakkaryの本番バインディング | 稼働中の `zakkary-web` は `VINEXT_KV_CACHE` に上記キャッシュnamespaceをバインドしている。調査時の稼働バージョンの短縮IDは `b03a84db`。Cloudflare上でGit連携は確認できなかった。                                                   |
| 共有上限                    | Workers FreeのKV書き込み上限はアカウント共通で1日1,000件。日次枠は00:00 UTC、09:00 JSTにリセットされる。                                                                                                                          |

**確定した障害原因**は、Zakkary Webのキャッシュが主な書き込み元となって共有の日次枠が尽き、DiaryのOAuthストアへの書き込みが失敗したこと。**未特定なのは**、Zakkaryのどのキャッシュ種別・ルート・操作が書き込みを増やしたかと、稼働中のVinext Workerを再現できるデプロイ元。

手元の `tomoki013/zakkaya-discovery` にはWebアプリ本体がある。確認した `main`（`f3f0b76`）の `apps/web/package.json` は `next build`、READMEはVercel配信を案内しており、Vinextアダプターと本番バインディングの設定は確認できていない。手元のソースと稼働中Workerが同一構成だと仮定せずに調査する。

参照先: [Zakkary Worker](https://dash.cloudflare.com/3429f85761059aeb24641592cb85645d/workers/services/view/zakkary-web/production)、[ZakkaryのKVメトリクス](https://dash.cloudflare.com/3429f85761059aeb24641592cb85645d/workers/kv/namespaces/404232716bf14504abdffac67410262c/metrics)、[DiaryのKVメトリクス](https://dash.cloudflare.com/3429f85761059aeb24641592cb85645d/workers/kv/namespaces/4554c3ab766c40eabb06afcea5da8beb/metrics)、[Workers KVの日次枠](https://developers.cloudflare.com/kv/platform/pricing/)。

## 2. 調査手順

### 2.1 本番を再現できるソースを特定する

1. Cloudflareの `zakkary-web` の **Deployments** で、現在稼働中のバージョンID、配信割合、デプロイ時刻、作成元、メッセージを記録する。CLIを使う場合は、認証済みアカウントとWorker名を確認し、読み取りコマンドを使う。

   ```sh
   pnpm exec wrangler deployments status --name zakkary-web
   pnpm exec wrangler deployments list --name zakkary-web
   version_id='稼働中の完全なバージョンID'
   pnpm exec wrangler versions view "$version_id" --name zakkary-web
   ```

2. デプロイ担当者のチェックアウト、CI成果物、リリース用ブランチまたは一時ディレクトリで、該当時刻とメッセージに一致するビルドを探す。次の文字列を、追跡済みソースと、該当ビルドの生成設定に対して検索する。

   ```sh
   git log --all --oneline -G 'VINEXT_KV_CACHE|kvDataAdapter|zakkary-web-vinext-kv-cache'
   rg -n 'VINEXT_KV_CACHE|kvDataAdapter|KVCacheHandler|setCacheHandler|zakkary-web-vinext-kv-cache' \
     -g 'vite.config.*' -g 'cloudflare.config.*' -g 'wrangler.*' -g 'package.json' \
     -g '*.ts' -g '*.mjs' -g '!**/node_modules/**' .
   ```

   Gitの無視対象にある生成ファイルは、対象のビルド出力先を指定し、`rg --no-ignore` で検索する。

3. 次の組を一つの再現手順として残す。ソースのリポジトリ・コミット、Vinextとアダプターの固定バージョン、ビルドコマンドとディレクトリ、Worker設定ファイル、アダプターを登録する場所、配信ドメインとバインディングの一覧。設定に含まれる認証情報の値は記録しない。
4. ソースとデプロイの対応を証明できない場合は、その点を明記し、デプロイ担当者に元の設定を確認する。ダッシュボードのバインディング名だけで、削除時の動作やフォールバックを判断しない。

コマンド参照: [Wranglerのデプロイ・バージョン確認](https://developers.cloudflare.com/workers/wrangler/commands/workers/#deployments)。

### 2.2 アカウントの日次枠と書き込み元を照合する

1. **Workers KV → 各namespace → メトリクス → リクエスト数**で、Zakkaryキャッシュ、Diary OAuth、その他のnamespaceを同じ期間で比較する。日次枠との比較は00:00 UTCからの集計を使う。ダッシュボードの「直近12時間」「直近24時間」は日次枠と境界が異なるため、正確な比較が必要なら [KVのGraphQL集計](https://developers.cloudflare.com/kv/observability/metrics-analytics/) の `kvOperationsAdaptiveGroups` を使う。
2. 時間別の書き込み増加、ZakkaryのWorkerリクエスト数、Diaryの `/analytics/oauth/token`・`/operator/oauth/token` の5xxを同じUTC時刻で並べる。表には成功件数と失敗件数が区別できるかを明記する。
3. Zakkaryの書き込み数を総リクエスト数で割った値も残す。アクセス量が違う時間帯を比較する場合は、合計件数とこの比率の両方を見る。

### 2.3 Zakkary内の書き込み経路を特定する

1. プレビューで、キャッシュの `get`・`set`・`delete` を**件数だけ**集計できるようにする。集計軸はルートの種類、データ／ページキャッシュの別、ヒット／ミス／再検証、無効化後の再生成。キャッシュキーの比較が必要な場合は、公開用に正規化したキーのハッシュを使う。検索語、座標、Cookie、トークン、店舗の未公開データ、レスポンス本文は記録しない。
2. 代表URLを少数固定し、コールド状態、同一URLの再読込、再検証期限後、店舗編集後の順に確認する。カテゴリごとに「1リクエスト当たりのキャッシュ書き込み」「オリジンAPI呼び出し」「応答時間」を記録する。
3. 以下は調査候補として優先する。**本番と同じアダプター構成を再現し、件数を観測してから原因として確定する。**

   | 候補                       | ソース上の根拠                                                                                                                                                                 | 検証方法                                                                               |
   | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
   | 検索条件の組み合わせ       | `apps/web/src/lib/public-catalog.ts` の `searchPublicStores` は条件のJSONごとに30秒キャッシュを持つ。店舗一覧は自由入力、タグ、絞り込み、カーソルなどを渡す。                  | 同一条件の繰り返しと、条件だけを変えたリクエストを比較し、新規キー数と再利用率を測る。 |
   | 店舗詳細・おすすめ         | 店舗詳細は店舗slugごとの30秒キャッシュ。`apps/web/src/lib/recommendations.ts` はエリア、最大3タグ、全体検索の最大5検索を並列実行する。クーポン利用後の提案には座標検索もある。 | 店舗詳細と提案APIを別々に計測し、1表示で生成されるキーと再検証回数を数える。           |
   | タクソノミーと無効化       | エリアとタグは60秒キャッシュ。店舗編集・写真公開などは `updateTag("public-stores")` を呼ぶ。                                                                                   | 編集の前後でどのキーが無効になり、次のアクセスで何件が再生成されるかを確認する。       |
   | データ以外の永続キャッシュ | Vinextの構成によっては、ページ／ISRのエントリもKVに保存される。                                                                                                                | アダプター設定と計測で、カタログデータ由来とページ生成由来の件数を分離する。           |

調査の完了条件は、上位の書き込み経路を**コード箇所と実測件数**で説明でき、再現手順を第三者が実行できること。トラフィックの多いルートを特定できない場合も、観測済みの範囲を示し、推測で確定扱いしない。

## 3. 修正方針

### 優先1: ZakkaryのキャッシュをKV書き込みから切り離す

実際のデプロイ元で、Zakkaryの公開データを保存しているKVアダプターをプレビュー構成から外す。確認したVinextのバージョンが対応していれば、データキャッシュを既定のメモリキャッシュに戻す。ページ用とデータ用で設定が分かれている場合は、KVに書く経路をそれぞれ確認する。

メモリキャッシュは拠点・実行環境をまたいで共有されない。コールド時のAPI負荷と、店舗更新後の別拠点での鮮度を確認する。更新直後の表示が必要な経路でキャッシュの整合性が不足する場合は、対象だけキャッシュを通さず取得するか、無効化を保証できる共有キャッシュを選ぶ。

ログイン、認証コールバック、管理・会員ページ、Cookieやセッションに依存する応答は共有キャッシュの対象から外した状態を維持する。適用単位はZakkaryのWebキャッシュ設定。DiaryのOAuth namespace、Access、Service Binding、トークン寿命は変更しない。

参照: [Vinextのキャッシュ方式とアダプター設定](https://github.com/cloudflare/vinext/blob/main/docs/caching.mdx)。実際に採用する構成は稼働版のドキュメント・実装と照合する。

### 優先2: 共有キャッシュが必要なら、保存対象と更新頻度を絞る

- **頻繁に再利用される公開データ**: 店舗詳細や定番のエリア・タグなどは、許容鮮度を確認した上で再検証を30〜60秒から**まず300秒**へ延ばし、1リクエスト当たりの書き込みが減るか測る。店舗更新時のタグ無効化は維持し、広すぎる無効化が原因だと計測で示せた場合は対象を絞る。
- **再利用率の低い検索**: 自由入力、任意座標、深いページ送り、複数条件の組み合わせは永続キャッシュから外す候補とする。営業中・クーポンのように時刻で結果が変わる条件は鮮度を別に扱う。検索の結果・並び順・ページングは維持する。
- **おすすめ欄**: 計測で書き込みの寄与が確認できた場合に、再利用しやすいエリア・タグの候補集合を共有するか、エリア候補で十分なときは追加検索を省く。変更前後で候補の重複と空欄率を比較する。
- **永続性が必要な場合**: 以上でAPI負荷や鮮度を満たせないときは、稼働版で対応するWorkers Response Storeなど、KV書き込みを消費しない方式を比較する。共有範囲、無効化、R2・Durable Objectsの使用量、切り戻し手順を先に確認する。

`ttlSeconds`（KVキーの保存期限）、`cacheTtl`（KVの読み取りキャッシュ）、アプリの `revalidate`（データを再検証する間隔）を区別する。どの値を変更するかは、書き込みを起こした処理を計測して決める。KV namespaceを同じアカウント内で分けても、日次書き込み枠は共通。

## 4. プレビュー検証と本番反映

1. **変更前の基準値を採る。** 同じ入力で、トップ、検索の先頭／次ページ、タグ・エリア、店舗詳細、おすすめ、店舗編集後の再表示、ログイン／ログアウトを確認する。通常リクエストと認証済みリクエストを分けて、HTTP結果、API呼び出し数、Worker CPU、p95応答時間、KV書き込みを記録する。
2. **修正候補を一つずつ比較する。** 優先1を先に評価し、必要なら優先2を追加する。対象経路のKV書き込みが0件になるか、アカウントに余裕ができる水準へ落ちることを確認する。KVを残す案の初期目標はZakkary **500件／UTC日以下**。これは共有枠に余裕を残すための運用目標で、実測と他namespaceの使用量を踏まえて調整する。
3. **レビュー時に差分と結果を提示する。** 修正したリポジトリ・ファイル、検証環境、変更前後の書き込み件数と比率、応答時間・API負荷の差、店舗更新直後の表示、切り戻し先の完全なWorkerバージョンIDをまとめる。本番反映は、内容と影響範囲を確認した後に行う。
4. **反映後、00:00 UTCから24時間観測する。** Zakkaryの書き込み件数とアカウント全体の件数を見て、1,000件の共有枠に余裕があることを確認する。APIの429・5xx、ログイン、店舗検索・店舗詳細、店舗編集の反映も確認する。すでに消費した日次枠は修正をデプロイしても戻らないため、次の09:00 JSTの枠リセット後を復旧判定に使う。
5. **Diaryの復旧を実機で確認する。** 既存Analyticsで週次・月次レポート、既存Operatorで読み取りツールを呼ぶ。その後、所有者が新URL `https://mcp.tomokichidiary.com/analytics/mcp` で再認可し、週次・月次タスクとD1の操作履歴を照合する。新旧のOAuth接続と実行結果を区別して記録する。
6. **切り戻し条件を定める。** ログインや検索・店舗詳細が失敗する、APIの429・5xxが増える、店舗更新が許容時間内に反映されない場合は、事前に控えたバージョンへ切り戻す。切り戻し後は、Zakkaryの機能とKV書き込みの増加を両方確認する。

## 5. 完了報告に含めるもの

- 稼働版とソースの対応表、変更ファイル、プレビューおよび本番のバージョンID。
- 共有枠の消費と、Zakkary内で書き込みを増やした経路を示す証拠。未特定の項目はその理由を記載。
- 変更前後の同条件でのKV書き込み、オリジンAPI呼び出し、HTTPエラー、応答時間、公開データの鮮度。
- 反映後の1日分のKV集計とDiaryのOAuth更新・新規認可、週次／月次の実行結果。認証情報や生のキーは添付しない。
