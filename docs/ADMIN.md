# 管理画面と公開

記事の正本は本番D1、写真の原本はR2です。Gitの `export/` は復元・コード検証用のスナップショットです。本番配信時はD1から公開版を取得して生成します。

## 記事を書く

1. [管理画面](https://admin.tomokichidiary.com/)へCloudflare Accessでログインし、記事から新規作成します。
2. タイトル・要約・Markdown本文を書きます。本文は200文字以上必要です。
3. 画像パネルでアップロード、またはライブラリから写真を選びます。代替テキストを入力し、一覧用の写真を「カバー」にします。
4. 本文の入れたい位置にカーソルを置き、写真の「本文に挿入」を押します。本文には通常のMarkdown画像が入ります。
5. 地域・カテゴリー・タグ・体験タグを選び、「すべて保存」（⌘S / Ctrl+S）を押します。各パネルの保存ボタンも同じ全体保存を行います。上部のバーはスクロールしても残り、各パネルへ移動できます。未保存のパネルには●が付きます。
6. プレビューを確認して「公開する」または「変更を公開」。未保存分も保存し、最新の内容を検証してから公開します。
7. 公開パネルの「サイト」が「反映済み」になると公開完了です。公開パネルにはこの記事の状態（下書き・予約・公開中、未公開の変更、サイトへの反映）が出ます。サイト全体の工程表示は反映中か失敗したときだけ出ます。生成中は旧公開版が表示されます。失敗した場合はログを確認し、反映を再試行できます。

固定ページにはカバーが不要です。予約公開は日本時間で設定でき、既存のGitHub Actionsが約5分ごとに期限の来た記事を検証・公開してサイトを生成します。実際の表示はビルド完了後になります。GitHub側の混雑で遅れることがあり、公開リポジトリで60日間活動がないと定期実行が停止するため、Actionsの「Publish content」を再有効化してください。CloudflareのCron Triggerや追加の有料枠は使いません。

未保存の変更がある状態で画面を移動すると確認が出ます。写真・関連付け・構造化データも対象です。Travel Knowledgeは必要な記事だけ開いて使えます。

本文パネルの「Markdownをコピー」で、画面上の本文（未保存分を含む）をそのままコピーできます。

## シリーズとタグ

サイドバー「シリーズ」でシリーズの一覧（公開記事数・URL・カバー）を確認し、作成・編集できます。

- 作成時に名前・slug・説明文・カバー画像（画像ライブラリから選択）・表示順を入力します。URL は `/collections/<slug>` で、slug は作成後に変更できません。削除はできません。
- 記事の所属は、記事編集の「関連付け → シリーズ・旅の記録」で選びます。1記事を複数のシリーズに入れられます。公開中の記事は「変更を公開」で所属が反映されます（下書きの所属は公開ページに出ません）。
- シリーズ内の記事の並びは、保存済みの順序 → 旅行開始日 → 公開日 → slug の順で決まり、ビルドごとに変わりません。
- 公開記事が0件のシリーズは noindex になり、サイトマップ・コレクション一覧・他シリーズへの導線に出ません。1件公開されると通常どおり表示されます。
- シリーズの作成・編集は次回のサイト反映で公開されます（記事の公開、または「サイトへの反映を再試行」）。
- タグは記事編集の「関連付け → タグ」の下にある入力欄から追加できます。slug・名前が既存タグと重複すると作成されません。

## Apple Music を埋め込む

本文に Apple Music の共有URLを **1行だけ** で書くと、公開ページと管理画面プレビューで Apple Music のプレーヤーになります。本文欄の下の「♪ Apple Musicを挿入」から、共有URLまたは Apple の「埋め込みコード」を貼り付けても同じ形で入ります。

- 曲：アルバム内の曲の共有URL（`…/album/…/123?i=456`）または `…/song/…`。小さなプレーヤーで表示します。
- プレイリスト・アルバム：`…/playlist/…/pl.…`、`…/album/…/123`。大きなプレーヤーで表示します。
- 文中のリンクとして書いた場合はプレーヤーにせず、通常のリンクのままです。
- アーティストページなど再生できないURLを1行で置くと、公開前チェックで止まります。

シリーズ「旅のサウンドトラック」では、音楽を扱う記事に `travel-music`（旅と音楽）、複数曲を紹介する記事にだけ `travel-playlist`（旅のプレイリスト）を付けます。

## 複数の記事をまとめて公開する

1. 写真を追加する各記事で「すべて保存」を押します。この時点では公開サイトは変わりません。
2. 記事一覧に戻り、「未公開の変更」で絞り込みます。
3. 公開したい記事のチェックを付けます。公開できる記事があると画面下にバーが出て、そこで「公開できる○件」をまとめて選択できます。
4. バーの「まとめて公開」を押します。各記事を検証し、公開できた記事をまとめてサイトへ反映します。
5. 「サイトに反映済み」で完了です。公開できなかった記事は一覧にタイトルと理由が出るので、修正・保存して再度公開します。

保存済みの下書きと、公開中の記事の未公開変更が対象です。予約・アーカイブ・変更のない公開版は選べません。絞り込みや検索を変更すると選択は解除されます。絞り込み・検索の条件は、記事を開いて一覧に戻っても同じタブの間は保持されます。本文・写真などの未保存分は一括公開に含まれないため、各記事で先に保存してください。固定ページも種別を切り替えて同じ操作で公開できます。

一括公開は全件成功を要求するトランザクションではありません。公開できた記事は反映し、チェックに通らない記事の旧公開版は維持します。ブラウザは記事ごとに既存の公開APIを呼び、最後に反映処理を1回起動します。D1の[1リクエストあたりのクエリ上限](https://developers.cloudflare.com/d1/platform/limits/)に収めるため、全記事の検証を1つのWorkerリクエストに詰め込みません。途中で画面を閉じても、成功した変更の反映待ちはDBに残り、定期実行が回収します。

## 自動反映の初回設定

GitHubの細粒度トークンを、対象リポジトリ `tomoki013/tomokichi-diary` のみに限定し、リポジトリ権限 **Actions: Read and write** で発行します。既存のGitHub Actionsを起動するために使います。コードを書き換えるContents権限や、Cloudflareの配信権限はWorkerに渡しません。

発行した値をAPIのsecret `GITHUB_PUBLISH_TOKEN` に登録します（チャットやGitには貼らない）。

```bash
pnpm --filter @tomokichi/api exec wrangler secret put GITHUB_PUBLISH_TOKEN --name tomokichi-diary-api
```

トークン期限切れや権限不足は管理画面で失敗として表示されます。更新後に「サイトへの反映を再試行」を押します。未設定の間はDBに公開版が保存されても、サイトの自動反映は行われず、その旨を表示します。

## 公開の流れ

APIは公開する版の本文・写真・関連付け・体験タグを記録し、`publish.yml` をmainで起動します。ワークフローは既存のGitHub production環境にあるCloudflare資格情報でD1を読み、R2の追加原本をチェックサムで確認して取得し、AstroとMCPを生成・配信します。exportをコミットする操作は不要です。

コードのmainへのマージ時も、同じD1の公開版から配信します。コード配信と記事配信は同じconcurrencyグループで直列化します。古い処理が後から完了しても、新しい公開要求を反映済みと扱いません。公開要求の正本は `site_publication`、実行ごとの工程・時間・エラーは `publication_builds`、公開時点の写真・関連付けは `publication_metadata` に保存します。

編集画面と一括公開欄には、サイト全体の「公開待ち → 公開データ準備 → 画像処理 → サイト生成 → 公開前チェック → 配信 → 反映確認 → 完了」を表示します。DBに公開版を保存した時点では「サイトに反映済み」にはなりません。実行固有の確認ファイルを配信先から取得できた後に完了になります。

経過時間・所要時間は公開要求の待ち時間を含みます。進捗割合や残り時間の推測は表示しません。ステータスの取得は既存の10秒間隔で、経過時間だけ画面内で更新します。工程が不要な場合は完了済みまたは省略になります。別の要求が実行中に新しい変更を公開した場合、新しい要求は公開待ちとして扱い、前の実行の完了・エラー・ログを新しい要求のものとして表示しません。

この表示はサイト全体のものです。現在開いている記事の未保存の変更・下書きや、別の記事が反映されたことを混同しないでください。記事ごとの「DBの公開版は最新です」はDB上の版を指します。失敗時はエラーコードと実行ログを確認し、「サイトへの反映を再試行」を押します。画面を閉じても処理は続き、未処理要求は5分間隔の定期実行が回収します。

`pnpm export:data` は引き続きローカルDBの書き出しです。本番D1の取得ではありません。本番配信用の取得処理は `scripts/content-release.ts pull` です。明示的なseedを除いて本番D1をGitのexportで上書きしません。

## Analytics

分析メニューで期間・前期間・記事別PV/検索実績・取得状況を確認できます。収益/検索語はAccess下だけで表示します。7/28/90日、月間、任意期間93日以内を選べます。再集計ボタンは最大31日の独立Actionsを起動します。概要のユーザー/sessionは取得済み日の期間uniqueです。任意93日以内は「期間人数を集計」で取得できます。期間cacheが日次より古い場合は—。日次人数はグラフから確認できます。—は欠損/未対応、0は確認済み0です。初回のWIF、D1集計保存、任意再集計token設定は [analytics/OPERATIONS.md](analytics/OPERATIONS.md) を参照。AdSense/ASP/AI未設定でもGA4/GSCを利用できます。

## 収益化

サイドバー「収益化」から広告方針、案件の下書き、配置予定、A/Bテストを管理できます。記事編集の「収益化」では本文プレビューから位置を選び、スロットの追加・移動・削除と案件の割当ができます。保存後は記事の「変更を公開」とサイト生成が必要です。アフィリエイトは管理画面プレビュー専用で、本番にはカード・リンク・空白枠を出しません。手順と切り戻し: [収益化 Phase 2](monetization-phase2.md)。
