# 管理画面と公開

記事の正本は本番D1、写真の原本はR2です。Gitの `export/` は復元・コード検証用のスナップショットです。本番配信時はD1から公開版を取得して生成します。

## 記事を書く

1. [管理画面](https://admin.tomokichidiary.com/)へCloudflare Accessでログインし、記事から新規作成します。
2. タイトル・要約・Markdown本文を書きます。本文は200文字以上必要です。
3. 画像パネルでアップロード、またはライブラリから写真を選びます。代替テキストを入力し、一覧用の写真を「カバー」にします。
4. 本文の入れたい位置にカーソルを置き、写真の「本文に挿入」を押します。本文には通常のMarkdown画像が入ります。
5. 地域・カテゴリー・タグ・体験タグを選び、「すべて保存」（⌘S / Ctrl+S）を押します。各パネルの保存ボタンも同じ全体保存を行います。
6. プレビューを確認して「公開する」または「変更を公開」。未保存分も保存し、最新の内容を検証してから公開します。
7. 「サイトに反映済み」になると公開完了です。生成中は旧公開版が表示されます。失敗した場合はログを確認し、反映を再試行できます。

固定ページにはカバーが不要です。予約公開は日本時間で設定でき、既存のGitHub Actionsが約5分ごとに期限の来た記事を検証・公開してサイトを生成します。実際の表示はビルド完了後になります。GitHub側の混雑で遅れることがあり、公開リポジトリで60日間活動がないと定期実行が停止するため、Actionsの「Publish content」を再有効化してください。CloudflareのCron Triggerや追加の有料枠は使いません。

未保存の変更がある状態で画面を移動すると確認が出ます。写真・関連付け・構造化データも対象です。Travel Knowledgeは必要な記事だけ開いて使えます。

## 自動反映の初回設定

GitHubの細粒度トークンを、対象リポジトリ `tomoki013/tomokichi-diary` のみに限定し、リポジトリ権限 **Actions: Read and write** で発行します。既存のGitHub Actionsを起動するために使います。コードを書き換えるContents権限や、Cloudflareの配信権限はWorkerに渡しません。

発行した値をAPIのsecret `GITHUB_PUBLISH_TOKEN` に登録します（チャットやGitには貼らない）。

```bash
pnpm --filter @tomokichi/api exec wrangler secret put GITHUB_PUBLISH_TOKEN --name tomokichi-diary-api
```

トークン期限切れや権限不足は管理画面で失敗として表示されます。更新後に「サイトへの反映を再試行」を押します。未設定の間はDBに公開版が保存されても、サイトの自動反映は行われず、その旨を表示します。

## 公開の流れ

APIは公開する版の本文・写真・関連付け・体験タグを記録し、`publish.yml` をmainで起動します。ワークフローは既存のGitHub production環境にあるCloudflare資格情報でD1を読み、R2の追加原本をチェックサムで確認して取得し、AstroとMCPを生成・配信します。exportをコミットする操作は不要です。

コードのmainへのマージ時も、同じD1の公開版から配信します。コード配信と記事配信は同じconcurrencyグループで直列化します。古い処理が後から完了しても、新しい公開要求を反映済みと扱いません。公開記録は `site_publication`、公開時点の写真・関連付けは `publication_metadata` に保存します。

`pnpm export:data` は引き続きローカルDBの書き出しです。本番D1の取得ではありません。本番配信用の取得処理は `scripts/content-release.ts pull` です。明示的なseedを除いて本番D1をGitのexportで上書きしません。
