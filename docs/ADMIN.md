# 管理画面と公開

記事の正本は本番D1、写真の原本はR2です。Gitの `export/` は復元・コード検証用のスナップショットです。本番配信時はD1から公開版を取得して生成します。

## 画面の構成

スマホ前提です。下のバー（PC では左）に「ホーム・記事・日記・写真・その他」があり、それ以外はすべて「その他」にまとまっています。画面上部の右には、サイトへの反映状態がいつも出ます（押すと「サイト反映」）。

- **ホーム**：「記事を書く」「日記を書く」「写真を上げる」と、いま手を付けるものの一覧です。反映の失敗、未公開の変更、予約公開、未対応の問い合わせ、確認待ちの事実、書きかけの下書きが、手を付ける順に並びます。押すとその画面に入ります。
- **その他**：シリーズ・タグ、ランキング、固定ページ、旅の知識、収益化、分析、問い合わせ、サイト反映、MCP 接続、操作ログ。

画面はすべて、API の操作（`POST /v1/admin/ops/<名前>`）を呼んで表示・保存します。操作の一覧は `packages/contracts/src/operations` にあり、MCP も同じ操作を使います（ADR 0011）。

## 記事を書く

1. [管理画面](https://admin.tomokichidiary.com/)へCloudflare Accessでログインし、「記事を書く」でタイトル・要約・slug を入れて下書きを作ります。URL はここで決まり、あとから変えられません。
2. 編集画面の上はタイトル・要約・本文です。本文の「写真」でライブラリから選ぶか、その場でアップロードしてカーソル位置に入れます。「プレビュー」は公開ページと同じ関数で描きます。本文は200文字以上必要です。
3. 「保存」を押します（上部のバーはスクロールしても残ります）。未保存のまま画面を離れると確認が出ます。
4. 「公開」パネルに、この記事の状態と公開前チェックの結果が出ます。「公開する」または「変更を公開」で公開します。未保存の変更があれば先に保存します。
5. 上部の「サイト反映済み」で公開完了です。

ほかのパネルは折りたたまれていて、必要なときだけ開きます。

- **SEO**：検索結果のタイトルと説明（空欄なら自動）、変更のメモ。
- **写真**：カバー・本文・ギャラリー・OGP の使い分け、代替テキスト、キャプション。本文に入れた写真は保存時に自動で加わります。
- **分類**：体験タグ、シリーズ、カテゴリー、タグ、地域（下の「関連付けの連動」）。
- **広告**：標準・末尾のみ、位置テスト、本文中の広告の位置直し。
- **旅の知識**：本文の事実（下の「旅の知識」）。

公開パネルからは、取り下げ（URL は残る）、アーカイブ、予約公開（日本時間）もできます。予約は既存の GitHub Actions が約5分ごとに期限の来た記事を検証・公開してサイトを生成します。GitHub 側の混雑で遅れることがあり、公開リポジトリで60日間活動がないと定期実行が停止するため、Actions の「Publish content」を再有効化してください。

固定ページ（プライバシーポリシーなど `/legal/`）は「記事」の「固定ページ」タブか「その他 → 固定ページ」から同じ編集画面で編集します。カバーは要りません。

### 複数の記事をまとめて公開する

記事一覧で、公開できる記事（下書き・非公開・未公開の変更あり）にチェックが出ます。選んで「まとめて公開」を押すと、1本ずつ公開前チェックをして公開し、最後にサイトを1回だけ作り直します。チェックに通らなかった記事は選んだまま残ります。全件成功を前提にしたトランザクションではなく、途中で画面を閉じても公開済みの分の反映待ちは DB に残り、定期実行が回収します。

## ともきちの一言日記

「日記」でタイトルだけ入れて書き始めます。要約・SEO・分類は求めません。

- 写真は任意です。本文の「写真」から入れるか、写真パネルで選びます。
- 投稿日は公開日と別に設定できます。空欄なら初回公開日です。
- 「関連する旅の記事」で記事を選べます。公開中の日記の変更は「変更を公開」するまで読者に出ません。
- 「取り下げる」は公開サイトから外します。「削除」は確認後に日記と URL を消し、元に戻せません。
- 一言日記は通常記事一覧・ランキング・サイト内検索に混ぜず、公開サイトの `/notes` と個別ページで読めます。

広告配置の `{{monetization:…}}` マーカーは単独の行にそのまま書きます。貼り付けた Markdown で波括弧やハイフンの前にバックスラッシュが入ると普通の文字列になり、公開チェックで止まります。

## 写真

「写真」でライブラリを検索（slug・ファイル名・使っている記事の地域）、アップロードします。同じ内容のファイルはハッシュで見つけて再利用します。大きい写真はブラウザで WebP に縮めてから上げられます。写真を押すと、公開 slug の変更、「画像生成 AI で作った」印、本文用の書き方のコピー、元画像の保存ができます。

## シリーズとタグ

「その他 → シリーズ・タグ」で一覧（公開記事数・URL）と作成、タグの追加をします。

- シリーズの URL は `/collections/<slug>` で、slug は作成後に変えられません。削除はできません。
- 名前・説明・カバー・表示順、テーマ曲、記事に付ける既定（タグ・カテゴリー・体験タグ）を編集します。既定は所属記事でよく使われているものを「いまの記事から提案を使う」で取り込めます。
- 記事の所属は記事編集の「分類」で選びます。公開中の記事は「変更を公開」で反映されます。
- 公開記事が0件のシリーズは noindex になり、サイトマップや一覧に出ません。
- シリーズの変更は次のサイト反映で公開されます。

## ランキング

「その他 → ランキング」で、トップページの「ともきち的ランキング」を編集します。名前・手書き風の添え書き・「もっと読む」の行き先（体験タグ）・表示順・写真1枚を決め、記事を探して1位から並べます（最大15本、上へ・下へで並べ替え）。各順位に一言（80文字まで）を付けられます。下書きの記事も入れておけますが公開されるまで出ません。公開中の記事が0本のランキングはトップページに出ません。保存は DB だけで、サイトには次の反映で出ます。

### 関連付けの連動

記事編集の「分類」で選んだものから決まるタグ類は自動で入ります（トーストで知らせます）。

- **シリーズ**：シリーズの「記事に付ける既定」のタグ・カテゴリー・体験タグが入ります。
- **地域**：地域や上位の地域と同じ名前のタグと、日本なら「国内旅行」、それ以外なら「海外旅行」が入ります。存在しないタグは作りません。

### テーマ音楽（シリーズ）

シリーズ編集の「テーマ曲」に Apple Music の曲・アルバム・プレイリストの共有 URL を入れ、「ページで流せるようにする」をオンにして保存すると、次のサイト反映でシリーズページと所属記事に「音楽と一緒に読む」が出ます。オフにしても URL は残ります。URL を消して保存すると設定ごと外れます。サーバー側でも Apple Music の URL だけを受け付け、iframe の HTML は保存しません。公開ページはボタンを押すまで Apple に通信せず、自動再生はしません。

## 旅の知識

記事の本文に書いてある事実（行った・乗った・いくらだった など）を1件ずつ持ち、確認済みのものだけをサイトの知識欄、構造化データ、公開 MCP に出します（ADR 0009・0011）。

1. **候補を出す**：記事編集の「旅の知識」で手入力するか、MCP につないだ ChatGPT・Claude に頼みます（例：「旅の知識がない記事を5本やって」→ `list_articles_without_knowledge` と `propose_travel_facts`）。どこから入れても「候補」です。一次体験の事実には体験した日が要り、空なら記事の旅行日が入ります。
2. **確認する**：「その他 → 旅の知識」の「確認待ち」で、記事をまたいで1件ずつ「確認」か「却下」を押します。確認できるのは管理画面の本人だけで、MCP からはできません。
3. 確認済みの事実の文面・日付・出どころを変えると、自動で候補に戻ります。

「未着手の記事」タブに、まだ知識のない公開記事が出ます。

## Apple Music を埋め込む

本文に Apple Music の共有URLを **1行だけ** で書くと、公開ページと管理画面プレビューで Apple Music のプレーヤーになります。本文欄に共有URLまたは Apple の「埋め込みコード」を貼り付けると、自動でこの形になります。

- 曲：アルバム内の曲の共有URL（`…/album/…/123?i=456`）または `…/song/…`。小さなプレーヤーで表示します。
- プレイリスト・アルバム：`…/playlist/…/pl.…`、`…/album/…/123`。大きなプレーヤーで表示します。
- 文中のリンクとして書いた場合はプレーヤーにせず、通常のリンクのままです。
- アーティストページなど再生できないURLを1行で置くと、公開前チェックで止まります。

シリーズ「旅のサウンドトラック」では、音楽を扱う記事に `travel-music`（旅と音楽）、複数曲を紹介する記事にだけ `travel-playlist`（旅のプレイリスト）を付けます。

## AI から操作する

ChatGPT や Claude から、管理画面でできることを MCP で操作できます（削除・問い合わせ・事実の確認・接続の失効を除く）。接続と権限は [OPERATOR_MCP.md](OPERATOR_MCP.md)。「その他 → MCP 接続」で接続の確認・名前付け・失効、「操作ログ」で誰がどの経路で何をしたかを見られます。

## 自動反映の初回設定

GitHubの細粒度トークンを、対象リポジトリ `tomoki013/tomokichi-diary` のみに限定し、リポジトリ権限 **Actions: Read and write** で発行します。既存のGitHub Actionsを起動するために使います。コードを書き換えるContents権限や、Cloudflareの配信権限はWorkerに渡しません。

発行した値をAPIのsecret `GITHUB_PUBLISH_TOKEN` に登録します（チャットやGitには貼らない）。

```bash
pnpm --filter @tomokichi/api exec wrangler secret put GITHUB_PUBLISH_TOKEN --name tomokichi-diary-api
```

トークン期限切れや権限不足は管理画面で失敗として表示されます。更新後に「その他 → サイト反映」の「サイトに反映する」を押します。未設定の間はDBに公開版が保存されても、サイトの自動反映は行われず、その旨を表示します。

## 公開の流れ

APIは公開する版の本文・写真・関連付け・体験タグを記録し、`publish.yml` をmainで起動します。ワークフローは既存のGitHub production環境にあるCloudflare資格情報でD1を読み、R2の追加原本をチェックサムで確認して取得し、AstroとMCPを生成・配信します。exportをコミットする操作は不要です。

コードのmainへのマージ時も、同じD1の公開版から配信します。コード配信と記事配信は同じconcurrencyグループで直列化します。古い処理が後から完了しても、新しい公開要求を反映済みと扱いません。公開要求の正本は `site_publication`、実行ごとの工程・時間・エラーは `publication_builds`、公開時点の写真・関連付けは `publication_metadata` に保存します。

「サイト反映」の画面に、サイト全体の工程（データ → 画像 → ページ生成 → 検査 → 配信 → 確認）を表示します。DBに公開版を保存した時点では「サイトに反映済み」にはなりません。実行固有の確認ファイルを配信先から取得できた後に完了になります。

経過時間・所要時間は公開要求の待ち時間を含みます。進捗割合や残り時間の推測は表示しません。ステータスの取得は既存の10秒間隔で、経過時間だけ画面内で更新します。工程が不要な場合は完了済みまたは省略になります。別の要求が実行中に新しい変更を公開した場合、新しい要求は公開待ちとして扱い、前の実行の完了・エラー・ログを新しい要求のものとして表示しません。

この表示はサイト全体のものです。現在開いている記事の未保存の変更・下書きや、別の記事が反映されたことを混同しないでください。記事ごとの「DBの公開版は最新です」はDB上の版を指します。失敗時はエラーとビルドのログを確認し、「サイトに反映する」を押します。画面を閉じても処理は続き、未処理要求は5分間隔の定期実行が回収します。

`pnpm export:data` は引き続きローカルDBの書き出しです。本番D1の取得ではありません。本番配信用の取得処理は `scripts/content-release.ts pull` です。明示的なseedを除いて本番D1をGitのexportで上書きしません。

## 分析

「その他 → 分析」で期間（93日以内）を選び、PV・ユーザー・検索・AdSense・アフィリエイトの概要と前期間、検索クエリ、記事別の数字と見直し候補、いいね、取得状況を見ます。取得状況のタブから再集計（31日以内）と期間人数だけの再集計（93日以内）を起動できます。—は欠損・未対応、0は確認済みの0です。初回の設定は [analytics/OPERATIONS.md](analytics/OPERATIONS.md)。

## 収益化

「その他 → 収益化」に、記事の広告（標準とのずれ）、位置テスト、アフィリエイト、設定のタブがあります。手順と切り戻し: [収益化 Phase 2](monetization-phase2.md)。

### 広告の標準ルール（2026-10-27）

広告の位置・状態・ユニットは手で選ばず、コードのルール（`packages/contracts/src/ad-layout.ts`）で決めます。管理画面と MCP の `set_ad_layout` は同じルールです。

- **標準**：記事末尾に1枠＋本文中に1枠。本文中の位置は「見出しと本文600字以上の後・画像／カード／埋め込みから離れた段落」から本文の約40%に近い段落を自動で選びます。すでに置いてある本文中の枠がルールを満たす場合はその位置を維持します。
- **末尾のみ** / **広告なし** も選べます。収益化モード（ads / affiliate / hybrid / none）は広告とアフィリエイト枠の有無から自動で決まります。
- アフィリエイト枠は標準化しても変えません。

**一括で揃える**：「記事の広告」タブで全記事を分類し、標準からずれている記事を「まとめて揃えて公開」で、本文（マーカーの追加・移動のみ）→ 広告設定 → 位置テスト終了の順に保存して公開します。公開中で未公開の変更がない記事だけが対象です。

**位置テスト**：記事編集の「広告 → 位置テストを始める」で、A（いまの本文中の位置）と B（離れた別の段落）を比べるテストを作り、「変更を公開」で開始します。A・B とも記事末尾の広告はあります。「位置テスト」タブで日数を確認し、終了できます（14日以上が判断の目安。終わったテストは再開せず、同じ記事の2回目は `-r2` 付きの新しい ID になります）。

**記事編集**：「広告」で「標準」「末尾のみ」「広告なし」を押すだけです。細かい配置は MCP の `save_article_ads` で指定できます。保存後に「変更を公開」が必要です。

プレビュー（下書き）では `{{monetization:…}}` マーカーの代わりに、読者に出る広告を枠で表示します（本文中・記事末尾は 300×250 の枠、アフィリエイトは案件名のカード、一時停止・未設定の枠は薄い「非表示の枠」、A/Bテスト中はBの枠に「半数の読者のみ」）。実際の広告は読み込みません。

## 公開状況の表示

記事の状態は1つの判定（`apps/admin/src/lib/article-state.ts` の `phaseOf`）から、記事一覧・編集画面で同じ言葉で表示します。

| 表示               | 意味                                               |
| ------------------ | -------------------------------------------------- |
| 下書き             | 一度も公開していない                               |
| 非公開             | 以前は公開していたが、いまは下書きに戻している     |
| 予約               | 公開日時を待っている                               |
| 公開中             | 保存済みの最新版を公開している                     |
| 公開中・変更未公開 | 公開中。保存した変更があり「変更を公開」で反映する |
| アーカイブ         | サイトに表示しない                                 |

「サイト」の表示（反映の開始待ち・反映中・反映済み・失敗）はサイト全体の配信の状態で、記事の状態とは別です。記事が一度反映された後に別の配信が失敗しても、その記事は「反映済み」のままです。
