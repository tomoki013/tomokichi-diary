# 管理画面・内部 MCP 作り直し 設計書（下書き）

状態: 下書き（2026-11-10）。本人レビュー前。ブランチ `feat/admin-rebuild-20261110`。

## 1. なぜ作り直すか

機能を継ぎ足してきた結果、1つの操作が4か所に別々に書かれている。

| 場所                                              | 書かれているもの                             |
| ------------------------------------------------- | -------------------------------------------- |
| `apps/api/src/routes/*.ts`                        | 処理の本体（ルートの中に処理が溜まっている） |
| `apps/admin/src/lib/api.ts`                       | 画面から呼ぶための型と関数                   |
| `apps/mcp-server/operator/client.ts`・`server.ts` | API を呼び直すクライアントと MCP ツール定義  |
| `apps/api/src/operator-policy.ts`                 | MCP に通してよい URL の正規表現              |

このため、管理画面でできるのに MCP でできない操作が多い（非公開、予約公開、メディアのアップロード、アフィリエイト案件など）。操作ログも URL を文字列で解析して操作名を作っている（`apps/api/src/app.ts`）。画面側は骨組みがなく、`Dashboard.tsx` は 2,544 行ある。

## 2. 決まっていること（本人判断、2026-11-10）

- 画面だけでなく内部構造も含めて全部作り直す。
- 操作の定義は1か所。管理画面と内部 MCP は同じ定義を使う。
- Worker の分け方は変えない（admin / api / mcp の3つ）。
- 作り直す MCP は内部用の Operator MCP と Analytics MCP。読者向けの公開 MCP（`/mcp`）は範囲外。
- Operator MCP は管理画面でできることを全部できる。例外は次のとおり。
  - 問い合わせ・メール: MCP に一切出さない（閲覧も不可）。
  - 削除: MCP に出さない。
  - MCP 接続の失効: 管理画面だけ。
  - 旅の事実の確認（候補を確認済みにする）: 管理画面で本人だけ。
  - 分析: Analytics MCP に出す（Operator とは別の MCP のまま）。
- 持ち越さない機能: 旧メッセージ、ダッシュボードのタスク・アイデア管理、URL の管理画面。
- 出し方は一括切り替え。全部できてから本番を切り替える。

## 3. 全体の形

```
packages/contracts/src/operations/   操作の仕様（名前・入力・出力・公開先・説明）
packages/application/src/operations/ 操作の本体（use case を呼ぶ）
        │
        ├─ apps/api        POST /v1/admin/ops/:name  … 認証・権限・操作ログをここ1か所で
        ├─ apps/admin      仕様から型が付く呼び出し  call("ranking.update", input)
        └─ apps/mcp-server 仕様から MCP ツールを自動で並べる（Operator / Analytics）
```

### 3.1 操作の仕様

1つの操作は次の項目を持つ。仕様は `packages/contracts` に置き、画面・API・MCP が同じものを import する。

| 項目          | 内容                                                                 |
| ------------- | -------------------------------------------------------------------- |
| `name`        | `ranking.update` のような「領域.動作」                               |
| `kind`        | `read` / `write` / `delete`                                          |
| `surface`     | `operator`（既定）/ `analytics` / `admin-only`                       |
| `input`       | zod スキーマ。API の検証、MCP の入力スキーマ、画面の型をここから作る |
| `output`      | 返す形の型                                                           |
| `description` | 日本語の説明文。MCP のツール説明にそのまま使う                       |
| `confirm`     | 公開など取り消しにくい操作で、MCP に確認用の入力を求める指定（任意） |
| `audit`       | 操作ログに残す対象の種類と、入力のどれが対象 ID か                   |

MCP に出るかどうかは `kind` と `surface` から機械的に決まる。手書きの許可リストは無くす。

- `surface: "operator"` かつ `kind` が `read` / `write` → Operator MCP に出る（`write` は書き込み権限のある接続だけ）。
- `kind: "delete"` と `surface: "admin-only"` → MCP に出ない。
- `surface: "analytics"` → Analytics MCP に出る。

`admin-only` にしてよいのは、問い合わせ（`inquiry.*`）、接続の失効（`connection.revoke`）、旅の事実の確認（`knowledge.verifyFact`）だけ。テストでこの一覧を固定し、ほかの操作を `admin-only` にすると落ちるようにする。これで「管理画面でできることは MCP でもできる」をコードで保証する。

### 3.2 API

- 入口は `POST /v1/admin/ops/:name` の1つ。いまの `/v1/admin/*` の約90ルートは無くす。
- 認証はいまと同じ（管理画面は Cloudflare Access、リモート MCP は Service Binding、ローカルは bearer token）。
- 権限の判定と操作ログは、この入口の1か所で仕様を見て行う。URL の文字列解析はやめる。
- 例外はファイルを扱う2つだけ: メディアのアップロード（multipart）と原本のダウンロード。入口は別だが、同じ仕様・同じ判定を通す。
- 読者向けの `/v1/contact`・`/v1/likes`・`/v1/images` と webhook、status probe は変えない。
- ルートに溜まっている処理（DTO の組み立てなど）は `packages/application` の read model と use case に移す。API は HTTP の受け渡しだけにする。

### 3.3 MCP

- **Operator MCP**（リモート・ローカルとも）: 仕様の一覧からツールを自動で登録する。読み取り専用の接続には `read` だけ並べる。`operator/client.ts` と `server.ts` の手書き約 970 行は無くなる。
- **Analytics MCP**: 同じ仕組みで `surface: "analytics"` の操作を並べる。OAuth の発行元・スコープ・接続先 URL は変えない。管理画面の分析画面も同じ操作を呼ぶ。
- OAuth、同意画面、接続の管理、操作ログの記録方法はいまの作りを引き継ぐ（#179〜#181 で入れたばかりで、問題の中心ではない）。
- ツール名はいまの 31 個を変えない。仕様の `mcpName` で指定する。

### 3.4 管理画面

- React + Vite の SPA、ハッシュルーター、Cloudflare Access はそのまま。依存は増やさない。
- 構成:

  ```
  apps/admin/src/
    app/        シェル（ナビ、ルーティング、サインイン、サイト反映の状態）
    data/       操作の呼び出しと、読み込み・再取得の共通フック
    ui/         共通部品（一覧、フォーム、メディア選択、確認ダイアログ）
    features/   領域ごと（下の表）。画面はここだけに置く
  ```

- 画面は「操作を呼んで見せる」だけにする。1ファイル 300 行を目安に分ける。
- 見た目は `docs/design/design-system.md` の v1.0（3色、スマホ前提、密度重視、軽いページ）。

| ナビ       | 中身                                                                                      |
| ---------- | ----------------------------------------------------------------------------------------- |
| ホーム     | サイト反映の状態、下書きと予約、未対応の問い合わせ件数、確認待ちの事実の件数（軽い1画面） |
| 記事       | 一覧、エディタ（本文・公開・紐づけ・メディア・広告・旅の知識）、法的ページ                |
| 日記       | 一言日記の一覧と編集                                                                      |
| まとめ     | シリーズ、ランキング（写真つき）、タグ                                                    |
| メディア   | ライブラリ、アップロード、重複確認                                                        |
| 収益化     | 全体設定、アフィリエイト案件、広告配置、広告テスト                                        |
| 分析       | ダッシュボード、記事別、体験別、いいね                                                    |
| 問い合わせ | チケット、返信、テンプレート、署名                                                        |
| 設定       | MCP 接続、操作ログ                                                                        |

### 3.5 ホーム画面の方針

スマホで開いて、数秒で「いま何をすればいいか」が分かり、そのまま手を付けられる画面にする。数字を眺める画面にはしない（数字は「分析」）。

- いちばん上に「書く」入口: 記事を書く、日記を書く、写真を上げる。
- その下に「やること」を1本の一覧で出す。種類ごとの箱に分けず、手を付ける順に並べる: 反映に失敗している、公開前チェックで止まっている下書き、予約公開の予定、未対応の問い合わせ、確認待ちの事実。各行から1タップで該当の画面に入る。
- やることが無いときは、その旨を1行で出すだけにする。
- サイト反映の状態は、全画面共通の細い帯で出す（ホーム専用にしない）。
- 読み込むのは件数と上位数件だけ。重い集計は載せない。

### 4.1 旅の知識の流れ（本人判断、2026-11-10）

機能は残し、流れを「候補を出す → 確認する → 公開される」に分ける。

1. **候補を出す**: MCP につないだ AI が記事を読み、事実の候補を MCP の操作で登録する。管理画面からの手入力もできる。どこから入れても状態は「候補」。MCP には知識が未着手の記事の一覧も出す。
2. **確認する**: 出どころ（一次体験・公式・調査・推定）に関係なく、確認済みにできるのは管理画面の本人だけ。記事をまたいだ「確認待ち」の一覧で、承認・修正・却下を選ぶ。確認済みの事実の文面や日付を変えたら、自動で候補に戻す。
3. **公開される**: サイト・構造化データ・公開 MCP に出るのは確認済みだけ（いまと同じ）。既存の 3 記事・15 件はそのまま使う。

無くすもの: API の中の AI による抽出（`suggestTravelFactCandidates`、`POST /knowledge/article/:id/suggestions`、管理画面の「提案の取得」）。本番では AI が未設定で動いていなかった。

いまとの違い: いまは一次体験の事実だけが確認操作を必須にしていて、ほかの出どころは保存時に確認済みにできる。確認済みの事実を書き換えても状態は戻らない。新しい作りではどちらも塞ぐ。ADR 0009 の「AI に一次体験の確認権限を与えない」はそのまま守り、範囲を全ての出どころに広げる（ADR を1本追加する）。

- ダッシュボードのタスク・アイデア: 画面、`/v1/admin/dashboard`、`packages/contracts/src/dashboard.ts`。`dashboard_tasks`・`dashboard_ideas` テーブル（migration 0026）は切り替えでは消さない。中のデータが要らないと本人が確認してから、別リリースで drop する。
- URL の管理画面: 画面と `/v1/admin/routes`。`routes` テーブル、公開側の解決、CI の整合性チェック（`pnpm check:routes`）は変えない。URL を動かす必要が出たら migration で行う。
- `apps/api/src/operator-policy.ts`、`apps/admin/src/lib/api.ts`、`apps/mcp-server/operator/client.ts`。

## 6. 進め方（一括切り替え）

作業はこのブランチで進め、本番には最後に1回で出す。

1. 土台: 操作の仕様の型、登録の仕組み、`/v1/admin/ops/:name`、権限と操作ログ、仕様を検査するテスト。
2. 操作を領域ごとに移す（記事 → 日記 → まとめ → メディア → 収益化 → サイト反映 → 設定 → 分析 → 問い合わせ）。操作ごとにテストを書く。
3. MCP をツール自動生成に置き換える（Operator のリモートとローカル、Analytics）。
4. 管理画面を新しい構成で書く（シェル → 領域ごと）。
5. 古いルート・クライアント・画面を消す。
6. docs（ADMIN、OPERATOR_MCP、ARCHITECTURE、DEVELOPMENT、analytics/CHATGPT、TESTING）と ADR を1本書く。
7. 切り替え: ローカルと preview で全操作を確認 → API、管理画面、MCP の順にデプロイ → `pnpm verify:mcp` と本番での確認。戻すときは3つの Worker を前のバージョンに戻す。DB の変更は無いので、戻しても壊れない。

作業中の注意:

- main に管理画面・MCP の機能追加を入れない（入れると二度手間になる）。入った場合はこのブランチを main に載せ直す。
- migration は追加しない前提。必要になったら追記のみ（expand → contract）。
